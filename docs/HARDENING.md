# اصلاحات امنیتی و یکپارچگی داده

این سند تغییراتی را توضیح می‌دهد که روی رفتار API اثر دارند، به‌ویژه برای تیم فرانت‌اند و هنگام deploy.

## ۱. دسترسی نقش‌ها

**مشکل قبلی:** حذف نقش از کاربر یا غیرفعال کردن نقش فقط فلگ `IsActive` را false می‌کرد، ولی هنگام ورود، نقش‌ها با `UserManager.GetRolesAsync` خوانده می‌شدند که این فلگ را نمی‌بیند. کاربر همچنان permissionهای نقش حذف‌شده را می‌گرفت.

**اکنون:**
- هنگام ورود و refresh فقط انتساب‌های فعالِ نقش‌های فعال حساب می‌شوند.
- access token حاوی «مهر امنیتی» (`sstamp`) کاربر است و **در هر درخواست** با وضعیت فعلی کاربر در دیتابیس مقایسه می‌شود (یک جستجوی ساده با کلید اصلی). بنابراین این تغییرات **فوراً** اعمال می‌شوند، نه بعد از ۱۵ دقیقه:
  - غیرفعال شدن یا حذف کاربر،
  - افزودن یا حذف نقش کاربر،
  - تغییر permissionهای یک نقش، تغییر نام یا (غیر)فعال شدن نقش،
  - تغییر رمز توسط ادمین.
- نقش `Admin` در هر راه‌اندازی برنامه، اگر غیرفعال شده باشد، دوباره فعال می‌شود (تا سیستم هیچ‌وقت بی‌ادمین نماند).

**اثر روی کلاینت:**
1. پس از تغییرات بالا، access token قبلی کاربر `401` می‌گیرد. کلاینت باید در این حالت یک بار `POST /api/Identity/RefreshToken` بزند و درخواست را تکرار کند. اگر دسترسی کاهش یافته باشد، توکن جدید برای آن endpoint `403` می‌گیرد.
2. توکن‌هایی که قبل از این تغییر صادر شده‌اند مهر امنیتی ندارند و یک‌بار رد می‌شوند. کاربران باید دوباره وارد شوند.
3. refreshها را در کلاینت سریالی کنید (هم‌زمان فقط یک refresh در حال انجام). اگر دو تب هم‌زمان با یک refresh token درخواست بدهند، فقط یکی موفق می‌شود و بقیه `401` می‌گیرند.

## ۲. Refresh token

- مصرف هر refresh token اتمیک است: از چند درخواست هم‌زمان با یک توکن فقط یکی برنده است.
- استفاده‌ی دوباره‌ی یک توکن ابطال‌شده، اگر کمتر از ۱۰ ثانیه بعد از ابطال باشد، `ConcurrentUse` (Warning) ثبت می‌شود و اگر دیرتر باشد `TokenReuseDetected` (Error، احتمال سرقت).
- ورودهای هم‌زمان یک کاربر با تلاش مجدد محدود مدیریت می‌شوند و `500` نمی‌دهند.
- توکن‌های منقضی یا ابطال‌شده‌ی قدیمی‌تر از ۳۰ روز هر ۲۴ ساعت پاک می‌شوند (job پس‌زمینه، ۵ دقیقه پس از شروع برنامه برای بار اول). تنظیمات: `Maintenance:RefreshTokenCleanup` در appsettings (`Enabled`، `RetentionDays`، `IntervalHours`، `InitialDelayMinutes`، `BatchSize`).

## ۳. حذف منطقی در داده‌های پایه

شامل Brand، EquipmentCategory، EquipmentLocationType، EquipmentModel، EquipmentStatus، EquipmentType، FailureCategory و SupportingDepartment.

| موضوع | رفتار جدید |
|---|---|
| عنوان یکتا | فقط رکوردهای **فعال** عنوان را اشغال می‌کنند. عنوان یک رکورد غیرفعال دوباره قابل استفاده است. (ایندکس یکتا روی دیتابیس فیلتردار شد: `WHERE IsActive = 1`) |
| لیست | پیش‌فرض فقط فعال‌ها. پارامتر جدید `isActive=false` فقط غیرفعال‌ها را برمی‌گرداند (برای پیدا کردن و بازگردانی) و `isActive=true` فقط فعال‌ها. `GET /{id}` همچنان رکورد غیرفعال را هم برمی‌گرداند. |
| غیرفعال‌سازی | اگر رکوردهای **فعال** وابسته داشته باشد `409` است. هم برای `DELETE` و هم برای `PUT` با `isActive=false`. |
| بازگردانی | `PUT` با `isActive=true` اگر عنوان توسط رکورد فعال دیگری اشغال شده باشد `409` و اگر والدش غیرفعال باشد `400` می‌دهد. |
| ساخت و ویرایش با والد غیرفعال | مدل روی برند یا نوع غیرفعال، و نوع روی دسته‌بندی غیرفعال، `400` می‌دهد. |

وابستگی‌ها: Brand ← مدل‌ها؛ EquipmentCategory ← نوع‌ها؛ EquipmentType ← مدل‌ها و تجهیزات؛ EquipmentModel، EquipmentStatus و EquipmentLocationType ← تجهیزات؛ FailureCategory ← انواع خرابی؛ SupportingDepartment ← کاربران و تجهیزات.

## ۴. کنترل هم‌زمانی (Optimistic Concurrency)

برای همان هشت منبع بالا:
- پاسخ جزئیات (`GET /{id}`، پاسخ ایجاد و ویرایش) فیلد جدید **`rowVersion`** (رشته) دارد.
- در `PUT` می‌توانید `rowVersion` را همان‌طور که خوانده‌اید برگردانید. اگر رکورد در این فاصله توسط کاربر دیگری تغییر کرده باشد، `409` برمی‌گردد و تغییر آن کاربر بازنویسی نمی‌شود. مقدار نامعتبر `400` است.
- ارسال نکردن `rowVersion` رفتار قبلی را حفظ می‌کند (آخرین نوشتن برنده است)، پس کلاینت‌های موجود نمی‌شکنند.
- بدون ستون جدید پیاده شده است (بر اساس `ModifiedDateTime`).

## ۵. خطاهای دیتابیس

- نقض کلید خارجی (SQL error 547) و ویرایش هم‌زمان اکنون `409` با پیام فارسی می‌دهند، نه `500`.

## ۶. ترتیب deploy

۱. migrationها را اعمال کنید:

```bash
dotnet ef database update --project EMS.Infrastructure --startup-project EMS.Presentation
```

(یا اسکریپت‌های idempotent در [`docs/sql`](sql): `AddAuditLog.sql` و سپس `CatalogIntegrity.sql`.) migration جدید فقط **ایندکس‌های عنوان** را عوض می‌کند و ستون یا جدول جدیدی نمی‌سازد. کد جدید با ایندکس قدیمی هم کار می‌کند؛ فقط تا اعمال migration عنوان رکوردهای غیرفعال هنوز در دیتابیس اشغال می‌ماند و ساخت عنوان تکراری خطای `409` می‌دهد.

۲. برنامه را deploy و راه‌اندازی کنید. در اولین راه‌اندازی seeder permissionهای جدید را به `Admin` می‌دهد و توکن‌های قدیمی رد می‌شوند.

## محدودیت‌ها

- هر درخواست احراز هویت‌شده یک query کوچک اضافه روی دیتابیس دارد. اگر بار بالا شد می‌توان نتیجه را چند ثانیه cache کرد (با هزینه‌ی تأخیر همان‌قدر در اعمال تغییرات).
- تست‌ها روی دیتابیس InMemory اجرا می‌شوند. اجرای migration و فیلتر ایندکس روی SQL Server واقعی، و تبدیل خطای 547 به `409`، با تست خودکار پوشش داده نشده‌اند.
- ورود جدید همچنان همه‌ی refresh tokenهای فعال دیگر همان کاربر را باطل می‌کند (یک نشست در هر لحظه).

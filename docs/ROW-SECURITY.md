# دسترسی سطح ردیف (RLS): زیرساخت

> **وضعیت: قاعده تعریف و اجرا شده** ([BUSINESS-DECISIONS.md ۳.۲۱](BUSINESS-DECISIONS.md)، [ADR-0027](adr/0027-row-security-rule-and-coverage.md)): هر کاربر داده‌های **ستاد خودش** و کارهای ارجاع‌شده به خودش را می‌بیند؛ دارندهٔ `DataScope.ViewAll` (و `Admin`) همه را. فاز ۱ (زیرساخت)، ۲ (جزئیات، نوشتن، مقصد، پیوست) و ۳ (کاربران، انتخاب تکنسین) اجرا شده‌اند؛ باقی‌مانده‌ها در پایین. تصمیم فنی زیرساخت: [ADR-0026](adr/0026-row-security-central-door-and-policies.md).

## ایده

هیچ سرویسی خودش بر اساس کاربر فیلتر نمی‌کند. همه چیز از **یک در مرکزی** (`IRowAccess`) می‌گذرد و هر قاعده در **یک سیاست** (`IRowPolicy<TRow>`) نوشته می‌شود:

```
درخواست ← توکن (کاربر و دپارتمان او) ← IDataScopeResolver ← DataScope
                                                              │
سرویس ← IRowAccess.Apply(ردیف‌ها) ← سیاست‌های نوع ردیف ←────────┘
                │
                └─ IRowAccess.RequireVisibleAsync(...)  ← جزئیات با شناسه و نوشتن (۴۰۴ اگر دیده نشود)
```

| بخش | کار | کجا |
|---|---|---|
| `DataScope` | چقدر داده‌ی این درخواست دیده می‌شود (`IsUnrestricted`، دپارتمان، **دلیل به زبان فارسی**) | `EMS.Application/Common/DataAccess` |
| `IDataScopeResolver` | **تنها جایی** که تصمیم می‌گیرد کاربر چقدر می‌بیند («ستاد مرکزی همه را می‌بیند» اینجا نوشته می‌شود) | `OpenDataScopeResolver` فعلاً همه را نامحدود می‌کند |
| `IDataScopeAccessor` | scope درخواست جاری، یک‌بار ساخته و کش می‌شود. بدون کاربر (راه‌اندازی، کارهای پس‌زمینه) = scope سیستم (نامحدود) | `EMS.Infrastructure/Security/RowSecurity` |
| `IRowPolicy<TRow>` | **یک شرط** (عبارت قابل ترجمه به SQL) برای هر مدل خواندنی؛ هم لیست، هم Excel، هم داشبورد، هم جزئیات و نوشتن همین را می‌پرسند | `EMS.Application/Security/RowPolicies` |
| `IRowAccess` | در مرکزی: `Apply` (کوئری)، `RequireVisibleAsync`/`IsVisibleAsync` (رکورد با شناسه)، `Describe` (توضیح) | `RowAccess` |

**هزینه:** scope از همان خواندنی ساخته می‌شود که اعتبارسنجی توکن در هر درخواست انجام می‌دهد (مهر امنیتی). دپارتمان کاربر در همان کوئری خوانده می‌شود، پس **کوئری اضافه‌ای نیست**.

## رفتارهای تضمین‌شده

- **scope نامحدود:** ردیف‌ها دست‌نخورده برمی‌گردند و سیاست‌ها اصلاً پرسیده نمی‌شوند.
- **scope محدود:** شرط سیاست‌ها به کوئری اضافه می‌شود (چند سیاست برای یک نوع با AND). سیاستی که `Filter` را `null` برگرداند «صراحتاً باز» است.
- **scope محدود و نوعی بدون هیچ سیاست:** **هیچ ردیفی دیده نمی‌شود** (امن به‌صورت پیش‌فرض) و در لاگ `Error` می‌آید. یعنی سیاستِ فراموش‌شده، داده لو نمی‌دهد؛ فقط خالی نشان می‌دهد.
- **رکورد با شناسه** (`RequireVisibleAsync`): اگر وجود ندارد یا دیده نمی‌شود، **همان `404`** با همان پیام و کد برمی‌گردد؛ تفاوتی از بیرون دیده نمی‌شود، پس وجود رکورد لو نمی‌رود. فقط وقتی رکورد *هست* ولی پنهان است، یک رویداد در **لاگ امنیتی** ثبت می‌شود (`Row access denied: user … asked for … outside his data scope (…)`)؛ فقط شناسه‌ها و دلیل scope، نه محتوا.

## ردیابی (traceability)

۱. **«چرا کاربر X این را نمی‌بیند؟»** `GET /api/RowSecurity/my-scope` برای کاربر واردشده: `isUnrestricted`، `supportingDepartmentId`، `reason` (به فارسی) و فهرست همه‌ی نوع‌های محافظت‌شده با قاعده‌ای که روی هر کدام اعمال می‌شود (`description`) و اینکه واقعاً او را محدود می‌کند یا نه (`restrictsYou`). هر کاربر فقط scope خودش را می‌بیند. (نمایش scope **کاربر دیگر** برای مدیر در فاز بعد.)
۲. **لاگ امنیتی:** هر دسترسی ردشده به رکوردِ موجود.
۳. **لاگ Debug:** هر بار که سیاستی کوئری را محدود می‌کند (نوع، کاربر، دلیل).
۴. توضیح هر سیاست در `Describe` همان متنی است که فرانت نشان می‌دهد؛ قاعده‌ی تازه = توضیح تازه در همان کلاس.

## تغییر قاعده یا افزودن نوع تازه

۱. **مقررات scope:** `IDataScopeResolver` را بنویس/عوض کن (مثلاً: دسترسی «مشاهده‌ی همه‌ی ستادها» یا ستاد مرکزی ⇒ نامحدود؛ وگرنه `DataScope.Restricted(userId, departmentId, "دلیل")`). یک کلاس، یک جا. اگر به داده‌ی بیشتری از کاربر نیاز است (مثلاً نقش)، از `DataScopeInput` می‌آید؛ برای داده‌ی تازه از دیتابیس، همان خواندن اعتبارسنجی توکن گسترش می‌یابد (`ValidateWithScopeAsync`).
۲. **سیاست هر نوع:** بدنه‌ی کلاس موجود را عوض کن (`OpenRowPolicy<T>` را به `RowPolicy<T>` تبدیل کن): `Filter(scope)` شرط را برگرداند، `Describe(scope)` آن را به فارسی بگوید. مثال:
   ```csharp
   public sealed class FailureReportRowPolicy : RowPolicy<FailureReportRow>
   {
       public override string Name => "FailureReport";
       public override string Describe(DataScope scope) => "گزارش‌های شعبه‌های زیر پوشش دپارتمان شما";
       public override Expression<Func<FailureReportRow, bool>>? Filter(DataScope scope)
       {
           var department = scope.SupportingDepartmentId;      // مقدار را در متغیر بگیر: پارامتر SQL می‌شود
           return r => r.SupportingDepartmentId == department;
       }
   }
   ```
۳. یک خط به `RowPolicySqlTranslationTests` اضافه کن (ترجمه به SQL Server).
۴. نوع تازه‌ی محافظت‌شده: یک کلاس `OpenRowPolicy<NewRow>` بساز و در سرویسش فقط از `VisibleRows` => `_access.Apply(...)` بخوان. ثبت در DI خودکار است.

## قواعدی که برنامه‌نویس باید رعایت کند

- **هر ردیف محافظت‌شده را فقط از `_access.Apply(...)` بخوان.** تست `RowAccessStructureTests` سورس را می‌خواند و خواندن بی‌واسطه‌ی `QueryRows` را رد می‌کند.
- **مسیرهای ساخته‌شده‌ی بعدی را همین‌طور بنویس:** رکورد با شناسه ← `RequireVisibleAsync` پیش از هر کاری؛ نوشتن ← اول `RequireVisibleAsync` روی رکورد، و برای مقصد (شعبه یا ستادِ جدید) بررسی دید مقصد.
- عبارت سیاست باید به SQL ترجمه شود؛ از متدهای کلاینتی در آن استفاده نکن.

## قاعده‌ی فعلی (خلاصه)

| کاربر | چه می‌بیند |
|---|---|
| دارای `DataScope.ViewAll` یا `Admin` | همه‌ی ستادها |
| کاربر ستاد X | تجهیز، گزارش و ارجاعِ ستاد X (تجهیز: نگه‌داشته‌ی شعبه‌های زیر ستاد X یا خودِ ستاد X؛ گزارش و ارجاع: شعبهٔ زیر ستاد X)، کاربران ستاد X، و کارهای ارجاع‌شده به خودش |
| کاربر بدون ستاد | فقط کارهای ارجاع‌شده به خودش (ارجاع، گزارش، تجهیز آن گزارش) و خودش |

شعبه‌ی بدون ستاد فقط برای «همه را می‌بیند»‌ها دیده می‌شود. داده‌ی مرجع (شعب، ستادها، کاتالوگ‌ها، سلسله‌مراتب) محدود نیست.

## مسیرها: چه چیزی از در می‌گذرد

| مسیر | چطور |
|---|---|
| لیست، Excel، داشبورد (تجهیز، گزارش، ارجاع، کاربران) | `_access.Apply` روی `VisibleRows`/`VisibleUsers` |
| رکورد با شناسه (جزئیات، تاریخچه‌ی مکان، تکنسین تجهیز، اقدام‌های ارجاع، تاریخچه‌ی ارجاع‌های گزارش) | `EnsureVisibleAsync` پیش از بارگذاری؛ ۴۰۴ برای پنهان و ناموجود یکسان |
| نوشتن (ویرایش، حذف، `move`، `bulk-move`، ارجاع، گذارها، کاربران) | همان بررسی پیش از `GetForUpdateAsync` |
| مقصد نوشتن (ثبت، `move`، گزارش جدید، ساخت و جابه‌جایی کاربر) | `IRowAccess.IsVisible(candidate)`: همان سیاست روی ردیفی که هنوز نیست |
| پیوست‌ها | `IAttachmentOwnerGuard` (فایل دیده می‌شود وقتی رکورد صاحبش دیده شود) |
| انتخاب تکنسین (dropdown، تکنسین تجهیز و ارجاع) | `UserDirectoryRow` / `TechnicianInfo` |

## آنچه هنوز محافظت **نمی‌شود** (آگاهانه)

- **یادداشت‌های ارجاع** (ماژول `AssignmentNote`): قاعدهٔ شرکت‌کننده‌ی خودش را دارد و به این در وصل نیست.
- **مدیریت ستادها و تخصیص شعبه به ستاد:** داده‌ی مرجع است؛ ولی جابه‌جایی شعبه بین ستادها دید دیگران را عوض می‌کند، پس فقط به مدیران داده شود.
- **نمایش scope کاربر دیگر برای مدیر** («چرا فلانی این را نمی‌بیند») هنوز نیست؛ هر کاربر scope خودش را می‌بیند.
- نام و مشخصات تکنسین و ارجاع‌دهنده داخل پاسخ ارجاع (`technicianName`، ...) از جست‌وجوی جدا می‌آید و محدود نمی‌شود (هویت شرکت‌کنندگان یک رکورد قابل‌دید).

## نوشتن تست برای کد تازه

نقش‌هایی که تست‌های عادی می‌سازند به‌طور پیش‌فرض `DataScope.ViewAll` هم می‌گیرند (`ApiTestBase.RolesSeeEveryDepartment`) تا درباره‌ی «چه کاری» باشند. برای تست دید، `RolesSeeEveryDepartment => false` را override کن و مثل `RowSecurityPipelineTests` کاربرانِ ستاد الف، ب، بدون ستاد و «همه» را بساز.

# شماره‌های موبایل پرسنل بانک

تصمیم فنی: [ADR-0033](adr/0033-employee-phone-numbers-and-report-upserts.md). شماره‌ها به `Employee` تعلق دارند و اطلاعات مشترک او هستند؛ گزارش خرابی فقط می‌تواند آن‌ها را اضافه یا ویرایش کند.

## جدول و مالکیت

`EmployeePhoneNumbers`: شناسهٔ `EmployeePhoneNumberId`، کلید خارجی `EmployeeId` و `PhoneNumber` الزامی، همراه `IsActive` و تمام فیلدهای `BaseEntity` برای ایجاد/ویرایش و Audit استاندارد. ارتباط کارمند یک‌به‌چند و بدون حذف آبشاری است.

هر شماره در کل جدول، **حتی میان رکوردهای غیرفعال**، یکتا است. یک شماره برای دو کارمند ثبت نمی‌شود. مالک یک رکورد شماره قابل تغییر نیست. با ویرایش A به B، شمارهٔ A آزاد می‌شود؛ حذف فیزیکی نیز شماره را آزاد می‌کند. تاریخچهٔ مالکیت جداگانه نداریم؛ Audit استاندارد پروژه همچنان برقرار است و برای رزرو شماره استفاده نمی‌شود.

ورودی موبایل ایران است: `09123456789`، `+989123456789` و `00989123456789` پذیرفته و به `09123456789` ذخیره می‌شوند. ارقام فارسی و عربی تبدیل و فاصله‌های ابتدا/انتها حذف می‌شوند. فاصله و خط تیرهٔ داخلی مجاز نیست. الگوی نهایی `^09[0-9]{9}$` است؛ این بررسی مالکیت سیم‌کارت یا فعال‌بودن شماره را استعلام نمی‌کند.

## CRUD مستقل

| مسیر | مجوز | رفتار |
|---|---|---|
| `GET /api/EmployeePhoneNumber` | `EmployeePhoneNumbers.View` | لیست صفحه‌بندی‌شده |
| `GET /api/EmployeePhoneNumber/{id}` | `EmployeePhoneNumbers.View` | جزئیات، شامل شمارهٔ غیرفعال |
| `POST /api/EmployeePhoneNumber` | `EmployeePhoneNumbers.Create` | ثبت شمارهٔ جدید |
| `PUT /api/EmployeePhoneNumber/{id}` | `EmployeePhoneNumbers.Update` | جایگزینی شماره و وضعیت فعال |
| `DELETE /api/EmployeePhoneNumber/{id}?rowVersion=...` | `EmployeePhoneNumbers.Delete` | حذف **فیزیکی** |
| `POST /api/EmployeePhoneNumber/bulk-delete` | `EmployeePhoneNumbers.Delete` | حذف فیزیکی گروهی در یک تراکنش |

ایجاد:

```json
{ "employeeId": 123, "phoneNumber": "09123456789" }
```

ویرایش (`employeeId` تغییر نمی‌کند؛ `isActive` پیش‌فرض true است):

```json
{ "phoneNumber": "09351234567", "isActive": true, "rowVersion": "0" }
```

حذف گروهی:

```json
{
  "items": [
    { "id": 45, "rowVersion": "0" },
    { "id": 46, "rowVersion": "0" }
  ]
}
```

شناسه‌ها و نسخه‌ها نمونه‌اند؛ `rowVersion` واقعی را از پاسخ رکورد بخوانید. نسخه اختیاری است؛ نسخهٔ قدیمی 409 می‌دهد. حذف تکی بدنه ندارد. در حذف گروهی ۱ تا ۱۰۰ شناسهٔ مثبت و بدون تکرار مجاز است؛ اگر یک رکورد یافت نشود، مجاز نباشد یا نسخه‌اش تعارض داشته باشد، **هیچ رکوردی حذف نمی‌شود**. خطاهایی مانند `items[1].id` یا `items[1].rowVersion` مورد مشکل‌دار را مشخص می‌کنند. حذف دوبارهٔ رکورد حذف‌شده 404 می‌دهد.

لیست: `employeeId`، `search` و `isActive` (پیش‌فرض true)، `pageNumber` از ۱ و `pageSize` بین ۱ تا ۱۰۰. مرتب‌سازی با `id`، `phoneNumber`، `createdDateTime`، `modifiedDateTime` و جهت `asc`/`desc`؛ شناسه ترتیب را قطعی می‌کند.

پاسخ شماره: `id`، `employeeId`، `phoneNumber`، `isActive`، شناسه و زمان ایجاد/ویرایش و `rowVersion`. تاریخ‌ها UTC هستند.

## ایجاد و ویرایش گزارش خرابی

هر دو DTO درخواست گزارش، `employeeId` و لیست اختیاری `employeePhoneNumbers` را می‌پذیرند:

```json
{
  "employeeId": 123,
  "employeePhoneNumbers": [
    { "phoneNumber": "09123456789" },
    { "id": 45, "phoneNumber": "09351234567", "rowVersion": "0" }
  ]
}
```

این نمونه بخش مربوط به کارمند است؛ سایر فیلدهای اجباری گزارش هم باید ارسال شوند.

- بدون `id`: افزودن شماره؛ مجوز `EmployeePhoneNumbers.Create` لازم است.
- با `id`: ویرایش شمارهٔ متعلق به همان کارمند؛ مجوز `EmployeePhoneNumbers.Update` لازم است. اگر هر دو نوع در لیست باشند، هر دو مجوز لازم‌اند.
- لیست غیرخالی، `employeeId` مثبت می‌خواهد. کارمند باید وجود داشته باشد و در دامنهٔ دسترسی تماس‌های کاربر باشد. فعال‌بودن کارمند و تطابق شعبهٔ او با شعبهٔ گزارش کنترل نمی‌شود.
- لیست null، خالی یا ارسال‌نشده، شماره‌های ذخیره‌شده را تغییر نمی‌دهد. نبودن شماره‌ای در لیست به معنی حذف نیست.
- شمارهٔ جدیدِ از قبل ثبت‌شده برای همین کارمند تکرار نمی‌شود؛ اگر غیرفعال باشد، همان رکورد دوباره فعال می‌شود. تکرار شماره‌های بدون id در همان درخواست پس از نرمال‌سازی یک بار اعمال می‌شود.
- شمارهٔ متعلق به کارمند دیگر، حتی غیرفعال یا خارج از دامنهٔ دید، 409 می‌دهد؛ اطلاعات مالک دیگر نمایش داده نمی‌شود.
- شناسهٔ شماره باید متعلق به `employeeId` انتخاب‌شده باشد؛ از این مسیر انتقال مالکیت نداریم. شناسه‌های تکراری و شمارهٔ مشترک میان دو ردیف ویرایشی رد می‌شوند. جابه‌جایی هم‌زمان شمارهٔ دو رکورد به یکدیگر پشتیبانی نمی‌شود.
- در هر درخواست حداکثر ۲۰ ردیف شماره پذیرفته می‌شود؛ تعداد کل شماره‌های کارمند به ۲۰ محدود نیست.
- تغییرات گزارش و شماره‌ها یک تراکنش دارند؛ شکست هر بخش، کل عملیات را برمی‌گرداند.

جزئیات گزارش در `employeePhoneNumbers` شماره‌های **فعال فعلی** کارمند را نمایش می‌دهد؛ برای نمایش، مجوز `EmployeePhoneNumbers.View` و دسترسی به کارمند لازم است، وگرنه آرایه خالی است. این snapshot تاریخی نیست؛ گزارش‌های قبلی نیز شماره‌های فعلی را نشان می‌دهند. تغییر کارمند گزارش یا حذف منطقی گزارش، شماره‌های کارمند قبلی را حذف یا منتقل نمی‌کند. لیست گزارش‌ها مجموعهٔ شماره‌ها را برنمی‌گرداند.

## دسترسی و خطاها

سیاست مرکزی `EmployeeContactRowPolicy` تماس‌ها را به پرسنل شعبه‌های زیر پوشش ستادهای کاربر محدود می‌کند؛ دامنهٔ نامحدود طبق سازوکار فعلی `DataScope` اعمال می‌شود. دسترسی به یک گزارش یا ارجاع به‌تنهایی دسترسی به شماره‌های همهٔ پرسنل را ایجاد نمی‌کند. شمارهٔ خارج از دامنه در مسیر شناسه مانند رکورد ناموجود 404 می‌دهد.

- ورودی نامعتبر: `400 validation_failed` با نام فیلد و پیام «شماره موبایل معتبر نیست؛ نمونهٔ صحیح: 09123456789».
- شمارهٔ تکراری: `409 employee_phone_number_taken` با پیام عمومی، بدون افشای مالک یا مقدار شماره.
- نسخهٔ قدیمی: `409 concurrency_conflict`.
- مجوز ناکافی: 403؛ رکورد ناموجود یا غیرقابل‌مشاهده: 404.

خطای یکتایی SQL در درخواست‌های هم‌زمان نیز از نگاشت استاندارد UnitOfWork به 409 تبدیل می‌شود. رویدادهای مدیریتی فایل لاگ فقط شناسه‌ها را ثبت می‌کنند.

## مایگریشن و تست

مایگریشن `20261114133547_EmployeePhoneNumbers` جدول، FK، ایندکس کارمند، ایندکس یکتای سراسری شماره و قید قالب شماره را می‌سازد. [اسکریپت idempotent](sql/EmployeePhoneNumbers.sql) نیز موجود است. جدول جدید است و داده‌های قبلی Employee یا User را تغییر نمی‌دهد. مایگریشن باید پیش از اجرای نسخهٔ جدید روی دیتابیس هدف اعمال شود؛ Down جدول و داده‌های آن را حذف می‌کند.

تست‌های API با EF InMemory و تست‌های واحد، CRUD، حذف گروهی، عدم حذف ضمنی، یکتایی میان کاربران مختلف، دسترسی، نسخه، نرمال‌سازی و قرارداد مدل را پوشش می‌دهند. تست ترجمهٔ SQL فقط کوئری تولید می‌کند و اتصال دیتابیس باز نمی‌کند. تست‌های متصل به SQL Server طبق درخواست صاحب محصول اجرا نمی‌شوند؛ اجرای واقعی مایگریشن و رقابت هم‌زمان SQL در این مرحله تأیید نشده است.

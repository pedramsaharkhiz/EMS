# ADR-0033: شماره‌های مشترک کارمند و ثبت همراه گزارش خرابی

- **وضعیت:** پذیرفته‌شده
- **ثبت‌شده در:** ۲۰۲۶-۱۱-۱۴

## زمینه

هنگام ثبت یا ویرایش گزارش خرابی باید بتوان موبایل‌های پرسنل بانک را برای استفادهٔ بعدی جمع‌آوری کرد. هر Employee چند شماره دارد، اما یک شماره نباید هم‌زمان برای دو کارمند ثبت شود. حذف فقط با API مستقل تماس‌ها انجام می‌شود. شرح قواعد کسب‌وکاری و قرارداد کامل در [EMPLOYEE-PHONE-NUMBERS.md](../EMPLOYEE-PHONE-NUMBERS.md) است.

## تصمیم

`EmployeePhoneNumber` یک موجودیت مستقل با FK به Employee، BaseEntity، Audit، IsActive و کنترل هم‌زمانی ModifiedDateTime است. شماره‌ها به شکل ۱۱ رقم انگلیسی با پیشوند 09 ذخیره می‌شوند و ایندکس یکتای بدون فیلتر در کل جدول دارند؛ غیرفعال‌شدن شماره را آزاد نمی‌کند. ویرایش مقدار یا حذف فیزیکی آن را آزاد می‌کند. تاریخچهٔ مالکیت جداگانه نداریم.

CRUD مستقل، حذف فیزیکی تکی و حذف گروهی اتمیک ارائه می‌شود. ورودی گزارش خرابی لیستی از `{ id?, phoneNumber, rowVersion? }` می‌پذیرد؛ بدون id افزودن/فعال‌سازی رکورد خود کارمند و با id ویرایش همان رکورد است. لیست جایگزین کل شماره‌ها نیست و هیچ حذف ضمنی انجام نمی‌دهد. سرویس تماس‌ها فقط تغییرات را stage می‌کند و سرویس گزارش، مالک تراکنش و save مشترک است؛ رویدادهای مدیریتی پس از commit ثبت می‌شوند.

مجوزهای مستقل EmployeePhoneNumbers و سیاست مرکزی EmployeeContactRowPolicy، دامنهٔ تماس‌ها را از طریق شعبهٔ کارمند کنترل می‌کنند. اعتبارسنجی فعال‌بودن کارمند یا تطابق شعبهٔ او با گزارش اعمال نمی‌شود؛ FK، وجود کارمند و کنترل دسترسی برقرارند. جزئیات گزارش شماره‌های فعال فعلی را تنها با مجوز مشاهده و دامنهٔ مناسب برمی‌گرداند؛ شماره‌ها snapshot گزارش نیستند.

## گزینه‌های بررسی‌شده

- ذخیرهٔ شماره روی گزارش: برای جمع‌آوری و نگهداری اطلاعات مشترک کارمند مناسب نیست.
- جایگزینی کل لیست هنگام PUT گزارش: شماره‌های قبلی را ناخواسته حذف می‌کند و رد شد.
- یکتایی فقط داخل Employee: اجازهٔ ثبت یک شماره برای دو کارمند می‌دهد و رد شد.
- تاریخچهٔ مالکیت شماره: به درخواست صاحب محصول اضافه نمی‌شود؛ پس از ویرایش یا حذف فیزیکی، شماره قابل استفادهٔ مجدد است.

## پیامدها

شماره‌ها در گزارش‌های بعدی قابل استفاده‌اند و مالکیت فعلی در دیتابیس تضمین می‌شود. حذف فیزیکی برگشت‌پذیر نیست؛ تاریخچهٔ Audit معمول پروژه، رزرو شماره ایجاد نمی‌کند. نقش‌های غیرمدیر برای مدیریت و مشاهدهٔ شماره‌ها باید مجوزهای جدید را دریافت کنند. تست‌های SQL واقعی طبق درخواست صاحب محصول اجرا نمی‌شوند؛ بررسی مدل و ترجمهٔ SQL جای آزمون واقعی اجرای مایگریشن را نمی‌گیرند.

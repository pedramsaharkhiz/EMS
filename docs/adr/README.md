# تصمیم‌های معماری (ADR)

هر فایل این پوشه **یک تصمیم فنی مهم** را همراه با دلیلش ثبت می‌کند، تا بعداً کسی (یا خودمان) بداند چرا کد این‌طور است و چه گزینه‌هایی رد شده‌اند.

## قاعده‌ها

1. **چه چیزی ADR می‌خواهد:** تصمیمی که عوض‌کردنش بعداً گران یا دردسرساز است یا روی چند ماژول اثر دارد (معماری، ذخیره‌سازی، احراز هویت و دسترسی، قالب API، ایندکس و ساختار دیتابیس، ابزار یا کتابخانهٔ مهم، راهبرد تست). تصمیم‌های کوچک و محلی نیاز ندارند.
2. **تصمیم کسب‌وکاری اینجا نیست:** قاعده‌های کسب‌وکار (مثل «سریال بین همهٔ تجهیزها یکتاست») در [`../BUSINESS-DECISIONS.md`](../BUSINESS-DECISIONS.md) ثبت می‌شوند. اگر تصمیمی هر دو جنبه دارد، ADR به آن لینک می‌دهد.
3. **یک تصمیم در هر فایل،** با نام `NNNN-عنوان-کوتاه-انگلیسی.md` و شماره‌ی بعدی.
4. **ADR تغییرناپذیر است.** اگر تصمیم عوض شد، فایل قدیمی را ویرایش نکن: ADR تازه بنویس، وضعیت قدیمی را به «جایگزین‌شده با ADR-NNNN» تغییر بده و در تازه به آن لینک بده.
5. **همین PR/کامیتی که تصمیم را اجرا می‌کند ADR را هم بیاورد.**
6. **صادق باش:** گزینه‌ای که واقعاً بررسی نشده را اختراع نکن. هزینه‌ها و ریسک‌های پذیرفته‌شده را بنویس.

## قالب

```markdown
# ADR-NNNN: عنوان

- **وضعیت:** پیشنهادی | پذیرفته‌شده | رد‌شده | جایگزین‌شده با ADR-NNNN
- **ثبت‌شده در:** تاریخ

## زمینه
مسئله چه بود و چه محدودیت‌هایی داشتیم.

## تصمیم
دقیقاً چه انتخاب شد.

## گزینه‌های بررسی‌شده
چه راه‌های دیگری بود و چرا رد شد.

## پیامدها
چه چیزی بهتر شد، چه هزینه یا ریسکی را پذیرفتیم، چه کاری بعدش لازم است.

## ارجاع
کد یا سند مرتبط.
```

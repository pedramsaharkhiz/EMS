# ADR-0019: حذف جدول `FailureReportActions`؛ اقدام‌ها فقط از راه ارجاع ثبت می‌شوند

- **وضعیت:** پذیرفته‌شده
- **ثبت‌شده در:** ۲۰۲۶-۱۱-۰۸
- **مرتبط:** [ADR-0018](0018-technician-assignment-workflow.md)

## زمینه
دو جدول برای «اقدام روی گزارش خرابی» داشتیم: `FailureReportActions` (گزارش↔اقدام، بدون زمان و توضیح) و `TechnicianAssignmentActions` (اقدامِ انجام‌شدهٔ تکنسین در یک ارجاع، با زمان و توضیح). هیچ‌کدام API نداشتند. هم‌پوشانی یعنی دو منبع حقیقت برای «روی این گزارش چه شد؟» اگر هر دو به کار می‌رفتند. مدیر تیم تأیید کرد جدول اول اضافه است.

## تصمیم
جدول، entity، پیکربندی، `DbSet`، مسیرهای ناوبری (`FailureReport.FailureReportActions`، `ActionEntity.FailureReportActions`) و بررسی وابستگی اقدام به آن حذف شد (مایگریشن `DropFailureReportActions`). اقدام‌های یک گزارش از راه ارجاع‌هایش (`GET /api/FailureReport/{id}/assignments` و اقدام‌های هر ارجاع) خوانده می‌شوند. وابستگی فعال کاتالوگ «اقدام» حالا فقط اقدام‌های ثبت‌شدهٔ ارجاع است.

## گزینه‌های بررسی‌شده
- **نگه‌داشتن جدول بلااستفاده:** رد شد؛ خطر استفادهٔ ناخواسته و دو منبع حقیقت، بدون هیچ سودی.
- **نگه‌داشتن آن برای «اقدام‌های برنامه‌ریزی‌شده روی گزارش»:** رد شد؛ چنین نیازی گفته نشده و اگر پیش آمد با مدل درست (نه این جدول) طراحی می‌شود.

## پیامدها
- اسکریپت `docs/sql/DropFailureReportActions.sql` جدول را حذف می‌کند؛ داده‌ای در آن نبود (API نداشت). اگر کسی دستی پر کرده، پیش از اجرا پشتیبان بگیرد.
- بازگشت (`Down`) جدول خالی را دوباره می‌سازد.

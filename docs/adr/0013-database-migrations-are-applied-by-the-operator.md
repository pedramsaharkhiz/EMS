# ADR-0013: مایگریشن دیتابیس را پیش‌فرض خود اپراتور اعمال می‌کند؛ اجرای خودکار هنگام شروع اختیاری است

- **وضعیت:** پذیرفته‌شده
- **ثبت‌شده در:** ۲۰۲۶-۱۱-۰۷

## زمینه
برنامه روی IIS مستقر می‌شود. تا اینجا هیچ جای کد مایگریشن اجرا نمی‌کرد: seederهای شروع برنامه فرض می‌کردند جدول‌ها از قبل هستند، و اگر مایگریشنی نخورده بود برنامه با خطای «جدول پیدا نشد» در همان لحظهٔ شروع می‌افتاد. چند مایگریشن ما روی داده‌های موجود شکست می‌خورند (مثلاً یکتایی سریال با سریال تکراری) و قبل از اجرا بررسی دستی لازم دارند.

## تصمیم
- **پیش‌فرض:** برنامه ساختار دیتابیس را تغییر نمی‌دهد. اپراتور مایگریشن‌ها را اعمال می‌کند (اسکریپت‌های idempotent در `docs/sql/` یا `dotnet ef database update`). اگر مایگریشنی جا مانده باشد، برنامه هنگام شروع یک **هشدار** با فهرست آن‌ها در لاگ می‌نویسد.
- **اختیاری:** با `Database:MigrateOnStartup = true` برنامه خودش مایگریشن‌های معوق را قبل از seederها اعمال می‌کند (`DatabaseMigrator`). پیش‌فرض `false` است و تست آن را قفل می‌کند.
- اگر مایگریشن حین شروع شکست بخورد، **برنامه بالا نمی‌آید** (عمداً؛ اجرا روی schema نیمه‌مایگریت‌شده بدتر است).

## گزینه‌های بررسی‌شده
- **همیشه خودکار:** حساب دیتابیس برنامه باید حق `ALTER/CREATE` داشته باشد (بهتر است فقط داده بخواند و بنویسد)، یک مایگریشن شکست‌خورده سایت را می‌خواباند، و چند نمونهٔ هم‌زمان ممکن است هم‌زمان مایگریشن بزنند. رد شد به‌عنوان پیش‌فرض.
- **هیچ‌وقت خودکار:** ساده و امن، اما برای محیط‌های کوچک یا توسعه که اپراتور جدا ندارند دست‌وپاگیر است. به همین دلیل گزینهٔ اختیاری نگه داشته شد.

## پیامدها
- استقرار Production با ریسک کمتر و حساب دیتابیس کم‌دسترسی ممکن است؛ هزینه: یک مرحلهٔ دستی پیش از هر استقرار که مایگریشن دارد.
- با روشن‌کردن گزینه، حساب دیتابیس برنامه باید حق تغییر ساختار داشته باشد. پیشنهاد: فقط در توسعه و محیط‌های تک‌نمونه، و با backup پیش از استقرار.
- تست خود مایگریشن‌ها روی SQL Server واقعی (`SqlMigrationStartupTests`) فقط با `EMS_TEST_SQL` اجرا می‌شود و تا امروز اجرا نشده است؛ این اولین تستی است که همهٔ مایگریشن‌ها را از دیتابیس خالی پشت‌سرهم اعمال می‌کند.
- قفل همزمانی چند نمونه به قابلیت‌های EF Core تکیه دارد و جداگانه آزموده نشده است.

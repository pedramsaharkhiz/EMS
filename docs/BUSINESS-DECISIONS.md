# تصمیم‌های کسب‌وکار

این سند **تنها مرجع تصمیم‌های کسب‌وکار** پروژه است. هر تصمیمی که صاحب محصول می‌گیرد (و قاعده‌ای که عمداً «فعلاً نگذار» گفته شده) همین‌جا ثبت می‌شود، با تاریخ و وضعیت. جزئیات فنی هر ماژول در سند خودش است و این‌جا فقط «چه چیزی تصمیم گرفته شد و چرا» می‌آید.

**چطور خوانده شود**
- **اجرا شده:** در کد هست.
- **تصمیم گرفته شد، اجرا نشده:** تصمیم قطعی است ولی هنوز کدی ندارد.
- **باز:** هنوز تصمیم نگرفته‌ایم. کد فعلاً رفتار پیش‌فرض (معمولاً «بدون محدودیت») را دارد.

> این سند از تصمیم‌هایی ساخته شده که در گفتگوهای اخیر با صاحب محصول گرفته شد. تصمیم‌های قدیمی‌تر که ثبت صریح نشده‌اند، هر وقت تأیید شدند اضافه می‌شوند. اگر چیزی با کد نمی‌خواند، کد یا همین سند را اصلاح کنید و هر دو را هم‌زمان نگه دارید.

## ۱. سمت کاربر (Post)  ·  اجرا شده  ·  ۱۴۰۵/۰۸/۱۳ (۲۰۲۶-۱۱-۰۴)

مستند فنی: [POSTS.md](POSTS.md)

| موضوع | تصمیم |
|---|---|
| مفهوم | هر کاربر می‌تواند یک «سمت» داشته باشد. نام: `Post`، مسیر: `/api/Post` |
| اجباری بودن | **اختیاری**. کاربر بدون سمت هم مجاز است |
| سمت‌های ثابت | سه سمت همیشه در دیتابیس هستند: تکنسین، مسئول واحد، ثبت‌کننده |
| ویرایش سمت‌های ثابت | فقط **عنوانشان** قابل ویرایش است. کدشان تغییر نمی‌کند و غیرفعال یا حذف نمی‌شوند |
| سمت‌های دیگر | برچسب ساده با CRUD کامل |
| قاعده‌ی کسب‌وکار | **فعلاً هیچ**. تکنسین، مسئول واحد و ثبت‌کننده فقط برچسب‌اند و کاری را مجاز یا ممنوع نمی‌کنند |
| رابطه با نقش | **مستقل**. تغییر سمت نقش را عوض نمی‌کند و برعکس |
| نمایش | در ورود (login)، لیست و جزئیات کاربر، و فیلتر لیست کاربران. (گروه‌بندی کاربران بعداً توسط تیم از پروژه برداشته شد) |

## ۲. ثبت گروهی تجهیز  ·  اجرا شده  ·  ۲۰۲۶-۱۱-۰۴

مستند فنی: [EQUIPMENT.md](EQUIPMENT.md#ثبت-گروهی)

| موضوع | تصمیم |
|---|---|
| منطق | مثل ثبت تکی است. فقط آرایه‌ای از تجهیزات از UI می‌آید |
| خطا در بعضی ردیف‌ها | **همه یا هیچ**. اگر یک ردیف خطا داشته باشد هیچ‌کدام ثبت نمی‌شود و خطای همه‌ی ردیف‌ها یک‌جا برمی‌گردد |
| محتوای هر ردیف | **کامل و مستقل**. هر ردیف نوع یا مدل، وضعیت و موقعیت اولیه‌ی خودش را دارد |
| سقف | ۲۰۰ ردیف در هر درخواست |
| یاس کد تکراری داخل درخواست | رد می‌شود (بدون توجه به حروف بزرگ و کوچک) |
| مجوز | همان `Equipments.Create`. مجوز جدا نداریم |
| تاریخچه و audit | برای هر تجهیز مثل ثبت تکی نوشته می‌شود |

## ۴. گزارش خرابی  ·  اجرا شده  ·  ۲۰۲۶-۱۱-۰۴

مستند فنی: [FAILURE-REPORTS.md](FAILURE-REPORTS.md)

| موضوع | تصمیم |
|---|---|
| وضعیت‌های گزارش | سه وضعیت ثابت: **باز**، **در حال رسیدگی**، **بسته**. ثبت همیشه «باز» شروع می‌شود |
| گذار بین وضعیت‌ها | **فعلاً هیچ قاعده‌ای نیست**. هر وضعیتی به هر وضعیتی می‌رود |
| ثبت‌کننده | از کاربر واردشده خودکار پر می‌شود و قابل ویرایش نیست. «کارمند گزارش‌دهنده» جداست و اختیاری |
| اثر روی تجهیز | **فعلاً هیچ**. ثبت یا بستن گزارش وضعیت و مکان تجهیز را عوض نمی‌کند |
| شعبه | همیشه کاربر انتخاب می‌کند و الزامی است. از مکان تجهیز پر نمی‌شود |
| شماره‌ی ارجاع | ورودی دستی و **اختیاری**. اگر داده شود بین گزارش‌های فعال یکتاست |
| اولویت | عدد ۱ تا ۵ با برچسب: ۱ کم، ۲ متوسط، ۳ بالا، ۴ خیلی بالا، ۵ فوری |
| زمان گزارش | اگر داده نشود زمان ثبت است. زمان آینده مجاز نیست |
| نوع‌های گزارش (ثابت) | خرابی، حادثه، ثبت شکایت، درخواست رسیدگی، نیاز به تعمیر/سرویس، نتیجه‌ی بازرسی |
| ارجاع به تکنسین و اقدام‌ها | **هنوز در دامنه نیست**. تسک جدا |
| API کارمند | **هنوز در دامنه نیست** |

## ۵. محدوده‌ی شعب برای ستاد پشتیبانی  ·  اجرا شده  ·  ۲۰۲۶-۱۱-۰۴

مستند فنی: [SUPPORTING-DEPARTMENTS.md](SUPPORTING-DEPARTMENTS.md)

| موضوع | تصمیم |
|---|---|
| هدف | هر ستاد پشتیبانی مشخص می‌کند برای کدام شعب‌ها پشتیبانی می‌کند |
| رابطه | **یک شعبه فقط یک ستاد دارد.** رابطه‌ی یک‌به‌چند است و جدول واسط لازم نیست (ستاد روی خود شعبه) |
| روش انتخاب | یک endpoint هم **شعبه‌به‌شعبه** و هم **گروهی** (ناحیه / زمینه‌ی کاری، مدیریت شعب یا حوزه) را می‌پذیرد و هم‌زمان هم قابل ترکیب است |
| معنای گروه | همه‌ی شعب **فعال** آن گروه در لحظه‌ی اختصاص. شعبه‌ی بعداً اضافه‌شده خودکار نمی‌آید |
| شعبه‌ی دارای ستاد دیگر | پیش‌فرض: **خطا** و هیچ تغییری ذخیره نمی‌شود. جابه‌جایی فقط با درخواست صریح |
| گزارش خرابی | لیست گزارش‌ها با ستاد پشتیبان (از روی شعبه‌ی گزارش) **فیلتر** می‌شود و ستاد در گزارش نمایش داده می‌شود |
| قاعده‌ی جغرافیایی | **هیچ.** نه شهر و نه استان. (تصمیم اولیه «استان یکی باشد» پس گرفته شد؛ شعبه فعلاً شهر و استان ندارد. اگر بعداً قاعده‌ای خواستید، فیلد جغرافیایی به شعبه اضافه می‌شود.) |
| غیرفعال‌سازی ستاد | ستادی که شعبه‌ی فعال دارد غیرفعال نمی‌شود |

## ۶. قرارداد کار با تیم

- پیام کامیت فقط شرح کار است و اسمی از ابزار یا مدل زبانی نمی‌آید.
- Pull Request فقط وقتی ساخته می‌شود که صاحب محصول بخواهد، و ادغام در `main` فقط با دستور صریح او.
- گذرواژه‌ی دیتابیس و اسرار در سند و کد ثبت نمی‌شوند.
